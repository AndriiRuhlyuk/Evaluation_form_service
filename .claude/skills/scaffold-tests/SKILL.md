Напиши тести для: $ARGUMENTS

Якщо `$ARGUMENTS` порожній - не вигадуй ціль. Виведи таблицю застосунків з кількістю
наявних тестів (`grep -c "def test_"` по кожному `tests*.py`), познач нулі і запитай,
який брати. Далі не йди.

## Крок 1 - прочитай, перш ніж писати

Прочитай сам модуль і його сусідів: `models.py`, `views.py`, `services.py`,
`permissions.py` того ж застосунку, плюс `urls.py` для реальних шляхів. Тести пишуться
з коду, а не з припущень про код. Якщо після читання незрозуміло, що є очікуваною
поведінкою - постав одне питання і чекай, замість вгадувати.

## Крок 2 - перевір, чи це вже не покрито

Перед писанням прогрепай наявні тести на ту саму поведінку:

```bash
grep -rn "def test_" --include="tests*.py" . | grep -v ".venv"
```

Три тести про одне й те саме гірші за один: вони створюють видимість покриття і всі
разом падають від однієї зміни. Якщо поведінка вже покрита в іншому застосунку -
скажи про це і не дублюй.

## Крок 3 - куди покласти файл

- є директорія `<app>/tests/` -> новий файл `<app>/tests/tests_<тема>.py`
- немає -> дописуй у наявний `<app>/tests.py`

Ніколи не створюй `<app>/tests.py` поряд з директорією `<app>/tests/` - Python не
вирішить, що таке `<app>.tests`, модуль чи пакет, і один з них зникне безслідно.

**Прибери заглушку.** `django-admin startapp` лишає файл із єдиним рядком
`# Create your tests here.`. Якщо такий знайшовся в цьому застосунку - запропонуй
видалити його разом зі своїм комітом:

```bash
find . -name "tests*.py" -size -100c -not -path "./.venv/*" -exec grep -l "Create your tests here" {} \;
```

Порожня заглушка нічого не ламає, але наступна людина відкриє її, побачить порожнечу
і вирішить, що застосунок не покритий.

## Крок 4 - конвенції цього репо

Еталон - `working_form/tests.py` і `question/tests/tests_questions.py`. Тримайся їх,
а не звичок з інших проєктів:

- `APITestCase` з `rest_framework.test`, не голий `TestCase`.
- `setUpTestData` для того, що спільне на весь клас; `setUp` - тільки для об'єкта,
  який кожен тест псує.
- URL пиши рядком з реальним шляхом (`f"/api/working-form/{obj.slug}/"`), **не** через
  `reverse()`. У репо lookup іде по `slug`, і рядок одразу показує, що тестується.
- Кожен тест перевіряє дві речі: HTTP-статус **і** стан рядка в базі. Тест, який
  дивиться лише на код відповіді, пропускає половину багів.
- Для м'якого видалення читай через `Model.all_objects`; `Model.objects` відфільтрує
  видалене, і тест виявиться зеленим через порожній результат.
- Назва: `test_<що робимо>_<що очікуємо>`, наприклад `test_second_delete_returns_404`.
- Коментар пояснює **чому** тест існує, а не що робить рядок. Мова коментарів -
  як у сусідньому файлі, не переписуй чужу.

## Крок 5 - що покривати першим

Порядок з `.claude/rules/testing.md`, не відступай без причини:

1. `services.py` - межі транзакцій і три функції `clone_*`, найбільша щільність багів.
2. `permissions.py` - доступ залежить від ролі **і** від участі у формі, тож помилка
   тут це витік даних, а не 500.
3. `working_form/consumers.py` - потребує `WebsocketCommunicator`, звичайний HTTP-клієнт
   туди не дістає.

Мінімум на один прохід: щасливий шлях, відмова за правами, і одна межа
(неіснуючий id, повторна дія, порожній список).

## Крок 6 - прожени і доведи

База живе в Docker, локальний `manage.py` до неї не достукається:

```bash
docker-compose up -d db redis
docker-compose exec -T celery python manage.py test <app>
black <app>
flake8
```

`flake8` мусить дати нуль знахідок - будь-який вивід це регресія від твого діфа.

Далі **обов'язково** прожени мутаційну перевірку. Вона по черзі псує конструкції
в цільовому файлі і дивиться, чи тести це помічають:

```bash
bash ${CLAUDE_SKILL_DIR}/scripts/verify-tests.sh <app> <шлях до цільового файлу>
```

Кандидатів шукає `scripts/mutate.py` через синтаксичне дерево, тому під перевірку
підпадають і багаторядкові вирази (`return (` на кілька рядків), і порівняння
(`a == b` стає `not (a == b)`). Кількість мутацій регулюється через
`MAX_MUTATIONS` (типово 5); коли кандидатів більше, вони беруться рівномірно по
файлу, а не поспіль від початку.

Цей крок не пропускається і не замінюється словами «тести виглядають коректно».
Покажи вивід скрипта як є.

Читай результат так:

- **усі спіймані** - тести реагують на поломку цього коду;
- **щось вижило** - рядок можна зламати, і жоден тест не почервоніє. Для кожної
  такої мутації скажи прямо: дописуєш тест чи свідомо лишаєш прогалину і чому;
- **пропущено (зламало синтаксис)** - це дефект мутатора, не сигнал про тести.
  Не тлумач це як добрий знак.

Покриття і мутації відповідають на різні питання. `coverage` каже, чи тести
**торкаються** коду; мутації - чи вони **помітять**, коли він зламається. Файл зі
100% покриття може не спіймати жодної мутації, і саме такий файл небезпечний:
цифра створює хибну впевненість.

## Крок 7 - звіт про розбіжності

Окремим розділом перелічи місця, де **заявлена** поведінка розійшлася з фактичною:
докстрінг обіцяє одне, код робить інше; клас дозволів оголошений, але недосяжний;
однакові дії в різних застосунках повертають різні коди.

Такі місця фіксуй тестом на **фактичну** поведінку і давай тесту назву, яка це
називає вголос (`test_is_employee_is_declared_but_never_applied`). Тоді той, хто
колись полагодить код, отримає червоний тест і буде змушений ухвалити рішення
свідомо, а не дізнатися про зміну з баг-репорту.

Не виправляй знайдене мовчки: розбіжність у поведінці це рішення власника продукту.

## Крок 8 - реєстр і коміт

Онови розділ "The real baseline" у `.claude/rules/testing.md`: додай новий файл і
одним рядком напиши, що саме він покриває. Реєстр, який відстав від реальності,
гірший за його відсутність.

Гілку створюй від `develop` за конвенцією README (`feature/*`), у `develop` напряму
не комітимо. Формат повідомлення:

```
Add: <app> test coverage for <що покрито>
```

Наприкінці окремим списком назви 2-3 випадки, які ти свідомо **не** покрив, і чому.
