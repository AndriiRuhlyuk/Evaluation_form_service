# Як ганяти евали цього скіла

Два набори, дві різні речі. `evals.json` міряє, **чи скіл робить правильно**;
`trigger-eval.json` міряє, **чи скіл узагалі спрацьовує** на тому, на чому має.

## Чому не `claude plugin eval`

Це був би правильний інструмент: він уміє арм без плагіна (`--ablation with-without`), тобто
базову лінію без скіла, і рахує дельту сам. Але на 2026-09-07 команда закрита за early access
і на цьому акаунті мовчки відмовляє:

```
$ claude plugin eval init --bare probe
`plugin eval` is currently in early access
```

Коли доступ зʼявиться, конвертувати варто: кожен кейс стає текою з `prompt.md` і `graders/*.md`
(схему брати з `claude plugin eval init --bare <name>`, а не вгадувати).

Поки що робочий harness це `example-skills:skill-creator` із субагентами: один арм на живий
скіл, другий на знімок попередньої версії.

## Два рівні кейсів

`tier: headless` - субагент проходить сам. Це ворота, зупинки й аудит: усе, що скіл вирішує
**до** того, як почати питати.

`tier: interactive` - потребує людини. Причина не в лінощах harness: середина цього скіла це
девʼять чекпойнтів `AskUserQuestion`, і субагент відповідає на них сам собі. Такий прогін
міряє самоузгодженість моделі, а не скіл. Гірше, він **виглядає як успіх**: документ виходить
повний і правдоподібний, бо його ніхто не заперечував.

Раніше весь набір ганявся як один рівень, і два кейси з пʼяти давали однаковий результат в
обох армах. Однаковий результат в обох армах означає, що кейс не міряє нічого.

## Прогін headless-рівня

```bash
# знімок попередньої версії - базова лінія
cp -r .claude/skills/requirements "$TMPDIR/skill-snapshot"
```

Далі на кожен кейс два субагенти в одному ході: один із живим скілом, другий зі знімком.
Зберігати вивід у `iteration-<N>/<case-id>/{with_skill,old_skill}/`, поряд `timing.json` із
`total_tokens` і `duration_ms` із повідомлення про завершення задачі - інде ці числа не
лишаються.

Далі `python -m scripts.aggregate_benchmark` і `eval-viewer/generate_review.py` зі скіл-крієтора.

## Що саме розрізняє версії

Більшість кейсів це запобіжники від регресії: обидві версії відмовляються писати PRD без
брифу, обидві зупиняються на двох стадіях. Це варто тримати, але це не вимірювання.

Розрізняє версії кейс **A4**, аудит наявного документа. Попередня версія мусила вручну пройти
одинадцять пунктів прози, розкиданих по трьох файлах, і на документі, чия секція критеріїв
називається не §5, стабільно проґавлювала поріг точки спостереження. Нова версія запускає один
скрипт, який цей поріг перевіряє незалежно від того, як секцію назвали.

## Тригерний набір

`trigger-eval.json` - двадцять запитів, десять на спрацювання й десять на нi. Близькі
промахи там навмисно близькі: стадія ідеї (це `discovery`), сховище й ендпоінти (це
архітектура), правка глосарію (це `fix-term-local`), тести на критерії, розбиття на задачі,
правка реєстру окремо від документа. Далекі промахи нічого не перевіряють.

Використання - крок «Description Optimization» у `example-skills:skill-creator`:

```bash
python -m scripts.run_loop \
  --eval-set .claude/skills/requirements/evals/trigger-eval.json \
  --skill-path .claude/skills/requirements \
  --model <id моделі цієї сесії> --max-iterations 5 --verbose
```

Він ділить набір 60/40 на train і test і обирає найкращий опис **за test**, а не за train.
Це важливо: опис, підігнаний під усі двадцять запитів, підігнаний під двадцять запитів, а не
під роботу.
