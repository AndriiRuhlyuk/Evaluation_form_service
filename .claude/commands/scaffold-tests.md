Напиши тести для: $ARGUMENTS

Якщо `$ARGUMENTS` порожній - не вигадуй ціль. Виведи таблицю застосунків з кількістю
наявних тестів (`grep -c "def test_"` по кожному `tests*.py`), познач нулі і запитай,
який брати. Далі не йди.

## Крок 1 - прочитай, перш ніж писати

Спершу прочитай сам модуль і його сусідів: `models.py`, `views.py`, `services.py`,
`permissions.py` того ж застосунку, плюс `urls.py` для реальних шляхів. Тести пишуться
з коду, а не з припущень про код. Якщо після читання незрозуміло, що є очікуваною
поведінкою - постав одне питання і чекай, замість вгадувати.

## Крок 2 - куди покласти файл

- є директорія `<app>/tests/` -> новий файл `<app>/tests/tests_<тема>.py`
- немає -> дописуй у наявний `<app>/tests.py`

Ніколи не створюй `<app>/tests.py` поряд з директорією `<app>/tests/` - Django
підхопить лише одне з двох, і другий файл мовчки не виконається.

## Крок 3 - конвенції цього репо

Еталон - `working_form/tests.py`. Тримайся його, а не звичок з інших проєктів:

- `APITestCase` з `rest_framework.test`, не голий `TestCase`.
- `setUpTestData` для того, що спільне на весь клас; `setUp` - тільки для об'єкта,
  який кожен тест псує.
- URL пиши рядком з реальним шляхом (`f"/api/working-form/{obj.slug}/"`), **не** через
  `reverse()`. У репо lookup іде по `slug`, і рядок одразу показує, що саме тестується.
- Кожен тест перевіряє дві речі: HTTP-статус **і** стан рядка в базі. Тест, який
  дивиться лише на код відповіді, пропускає половину багів.
- Для м'якого видалення читай через `Model.all_objects`; `Model.objects` відфільтрує
  видалене і тест виявиться зеленим через порожній результат.
- Назва: `test_<що робимо>_<що очікуємо>`, наприклад `test_second_delete_returns_404`.
- Коментар пояснює **чому** тест існує, а не що робить рядок. Мова коментарів -
  як у сусідньому файлі, не переписуй чужу.

## Крок 4 - що покривати першим

Порядок з `.claude/rules/testing.md`, не відступай від нього без причини:

1. `services.py` - межі транзакцій і три функції `clone_*`, найбільша щільність багів.
2. `permissions.py` - доступ залежить від ролі **і** від участі у формі, тож помилка
   тут це витік даних, а не 500.
3. `working_form/consumers.py` - потребує `WebsocketCommunicator`, звичайний HTTP-клієнт
   туди не дістає.

Мінімум на один прохід: щасливий шлях, відмова за правами, і одна межа
(неіснуючий id, повторна дія, порожній список).

## Крок 5 - прожени і покажи результат

База живе в Docker, тож локальний `manage.py` до неї не достукається:

```bash
docker-compose up -d db redis
docker-compose exec -T celery python manage.py test <app>
black <app>
flake8
```

`flake8` мусить дати нуль знахідок - будь-який вивід це регресія від твого діфа.

Далі **доведи, що тест справді щось перевіряє**: тимчасово зламай перевірену поведінку
(поверни не той статус, прибери фільтр), покажи червоний прогін, поверни код назад,
покажи зелений. Тест, який не червонів, нічого не доводить.

## Крок 6 - оновіть реєстр і закомітьте

Онови розділ "The real baseline" у `.claude/rules/testing.md`: додай туди новий файл і
одним рядком напиши, що саме він покриває. Реєстр, який відстав від реальності, гірший
за його відсутність.

Гілку створюй від `develop` за конвенцією README (`feature/*`), у `develop` напряму не
комітимо. Формат повідомлення:

```
Add: <app> test coverage for <що покрито>
```

Наприкінці окремим списком назви 2-3 випадки, які ти свідомо **не** покрив, і чому.
