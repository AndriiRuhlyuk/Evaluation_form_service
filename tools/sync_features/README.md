# sync_features

Агент на `claude-agent-sdk`, що звіряє `Features_list.json` (реєстр фіч цього
репозиторію, ведеться вручну) із git-історією: читає коміти, знаходить
розбіжності з реєстром і сам вносить дозволені правки - переключає `"done"` і
додає нові записи. Не частина продукту `evaluation_form_service` -
інструмент розробника, окремий venv, не в `requirements.txt` сервісу.

Специфікація і план: `docs/plans/2026-08-28-sdk-sync-features-spec.md`,
`docs/plans/2026-08-28-sdk-sync-features.md`. Секції `5`, `5.1`-`5.3` цього
документа - джерело знахідки про `PreToolUse` hook нижче; тут вона лише
переказана, без повторення дослівних цитат.

## Опис на 3-5 речень (R6)

Use case - синхронізація `Features_list.json` (84 записи, серії id
AUTH/CORE/TPL/.../ARCH/CFG/FE) із git-історією: реєстр ведеться вручну і
дрейфує від реальних комітів, а агент читає `git log`, зіставляє id фіч у
темах комітів із полем `"done"` і сам вносить правки. Access mode - Python
SDK (`claude-agent-sdk`), а не CLI напряму: проєкт на Python, і SDK віддає
типізовані події (`AssistantMessage`, `ResultMessage`) замість парсингу JSON
з stdout підпроцесу вручну. Три виміри дозволів (детально нижче) - `Bash`
обмежений білим списком опцій `git log`, `Read` - лише `Features_list.json`
і рівно `<app>/services.py`, `Edit` - лише `Features_list.json`; усі три
гейтяться одним `PreToolUse` hook, не `allowed_tools`. Найскладніше в
налаштуванні JSON-схеми відповіді агента - не типи полів самі по собі
(`verify.OUTPUT_SCHEMA` це покриває прямолінійно), а те, що схема мусить
дати агентові спосіб сказати "я це розглянув і свідомо НЕ чіпав": зв'язок
"коміт -> id фічі" виявився N:M, не 1:1 (виміряний факт: коміт `7f6861e`
згадує п'ять id одразу - `ARCH-20..22`, `CFG-1`, `CFG-2`), а більшість цих
згадок приходить з комітів `Docs:`, які ФІКСУЮТЬ знахідку, а не реалізують
її. Тому відповідь має три списки, не два - `flipped_to_done`,
`new_entries` і `left_unchanged` - і інваріант покриття (I4) вимагає, щоб
кожен id з комітів був ВРАХОВАНИЙ хоч в одному з них; без третього списку
чесний агент, який правильно нічого не змінив, провалював би I4 на кожному
реалістичному прогоні (див. "Finding J" нижче).

## Чому пісочниця стоїть на `PreToolUse` hook, а не на `allowed_tools`

Лекційний матеріал курсу описує `--allowed-tools`/`allowed_tools` як межу
рівня файлової системи. Спец, розділ 5, цитує README пакета `claude-agent-
sdk` дослівно: це allowlist на **авто-схвалення**, і пакет прямо каже, що
він **не прибирає** інструменти з набору моделі - блокування дає лише
`tools=[...]` (склад набору) або `disallowedTools`. Цей проєкт **виміряв**
це емпірично (спец, розділ 5, CLI-прогін): з `allowedTools` на рівні
`Bash(git log:*)` агент виконав `echo GATE_9137` без жодного відхилення.

Спец, розділ 5.1, розбирає, чому очевидна заміна - `can_use_tool` -
ненадійна: обов'язковий streaming-режим (інакше callback не викликається
взагалі, без помилки), затінення записом, що дозволяє інструмент цілком
(`CanUseToolShadowedWarning`, показується раз на процес - легко пропустити),
і повне вимкнення в `permission_mode="bypassPermissions"`. Розділ 5.2:
пакет сам двічі повторює в коді - "To gate every tool call, use a
PreToolUse hook instead." Розділ 5.3 - підтверджений робочий механізм,
той самий, що використовує `guard.pre_tool_use_hook` тут:
`ClaudeAgentOptions(hooks={"PreToolUse": [HookMatcher(matcher="*", ...)]},
setting_sources=[])`. `setting_sources=[]` обов'язковий окремо -
allow-правило в `.claude/settings.json` затінює callback ще ДО охоронця,
і SDK цього не покаже.

### `make run` - позитивний прогін, Finding H (Task 7, ревʼю раунд 3)

Контролер запустив `make run` наживо в цьому worktree (навмисно тут, не в

  продуктовий промпт.
- **H2** - DENY-причини `guard.py` тепер називають ПРИЙНЯТНУ форму (див.
  "Три виміри дозволів" вище) - reader цих рядків не людина, а сам агент,

- **H3** - `MAX_TURNS` піднято з 20 до 40 - реальна робота (git log + Read

### Finding I (Task 7, ревʼю раунд 4) - формат відповіді агента

**I1 - артефакт не зберігав сиру відповідь агента при провалі парсингу.**
Той самий прогін коштував ~$0.10 і 103 секунди, а збережений
`sync-report.md` показував лише:

```
## JSON агента

(відсутній - JSON агента не розпарсився: агент повернув не JSON: Expecting value: line 1 column 1 (char 0))
```

- жодного способу зрозуміти, ЩО саме сказала модель, без ще одного
платного прогону. Тепер `_write_journal` приймає `raw_agent_text` -
`main_sync` передає його з ДВОХ місць: коли `parse_agent_json` провалюється
(payload так і лишається `None`) і коли `validate_schema` знаходить
порушення (payload є, але щось у ньому не так - сирий текст іде поруч, щоб
не гадати, як payload розійшовся з тим, що написав агент). Нова секція
`## Сира відповідь агента` - лише на цих двох шляхах; на успішному вона не
з'являється, бо `payload` там уже несе всю інформацію. Текст обрізається
на 4000 символів (`_RAW_TEXT_TRUNCATE`) з видимою міткою "...(обрізано,
повна довжина N символів)".

**I2 - `parse_agent_json` не переживав прозу навколо JSON.** Функція
знімала ```` ``` ```` лише коли ВЕСЬ текст ПОЧИНАВСЯ з неї
(`text.startswith("```")`) - модель, що відкриває відповідь реченням
"Here is the result:", ламала парсинг структурно, хоча сам JSON був
правильний. Контролер виміряв це локально (без мережі) на шести формах
відповіді - таблиця нижче, "до" і "після":

| форма | до | після |
|---|---|---|
| голий JSON | OK | OK |
| огорожа ```` ```json ```` | OK | OK |
| проза ПЕРЕД огорожею | `None` (`Expecting value: line 1 column 1`) | OK |
| проза ПІСЛЯ огорожі | `None` (`Extra data: line 2 column 1`) | OK |
| проза ПЕРЕД JSON (без огорожі) | `None` (`Expecting value: line 1 column 1`) | OK |
| чиста проза | `None` | `None` (НЕ змінено - жорстка вимога) |

`parse_agent_json` тепер шукає fenced-блок (```` ```json ```` або гола
```` ``` ````) БУДЬ-ДЕ в тексті; якщо огорож немає - найзовнішній
збалансований `{...}` (від першої `{` до її парної `}`, з урахуванням
рядкових літералів); якщо й цього немає - весь текст як є, і `json.loads`
сам дає ту саму помилку, що й раніше. Чиста проза й надалі МАЄ повертати
`None` - R5 (доказ обробки помилок) залежить саме від цього.

Дві жорсткі вимоги, обидві дотримані: (1) чиста проза не парситься НІКОЛИ
(тест `test_shape_6_pure_prose_returns_none`); (2) огорожа - пріоритетна,
збалансований діапазон - лише fallback, коли огорож немає взагалі, НЕ
друга спроба після невдалого парсингу огорожі - щоб чужий `{...}`,
процитований моделлю десь у прозі поруч, ніколи мовчки не "полагодив"
зламану відповідь. Якщо огорож декілька - береться ОСТАННЯ (типовий
патерн моделі: приклад чи чернетка спершу, підсумкова відповідь
наприкінці) - перевірено тестом, де агент цитує приклад JSON, а потім дає
іншу реальну відповідь: обирається саме друга, реальна.

Обидва фікси - у коді, не в промпті: `PROMPT` просити суворіший формат
(лише JSON, без жодного тексту навколо) можна, але це прохання, не
гарантія - парсер мусить пережити модель, яка це прохання проігнорує.

[verify] схема OK
[verify] інваріант: id з комітів відсутні у відповіді агента: ARCH-20, ARCH-23, ARCH-24, CFG-1, CFG-2
{"flipped_to_done": [], "new_entries": []}
```

Стан цих п'яти в реєстрі: `ARCH-20 done=True`, решта `done=False`. Усі
п'ять згадані в комітах з префіксом `Docs:` - комітах, які ФІКСУЮТЬ
знахідку, а не повідомляють про її усунення (`Docs: ARCH-23 - CI матриць
читає лише код виходу` реєструє проблему, а не рішення). Агент виконав
рівно те, що казав промпт:

> If a commit is ambiguous, leave it alone and **say nothing about it**.

I4 вимагав протилежного - щоб кожен id з комітлогу був у відповіді, - а
місця для "розглянув і НЕ змінив" у схемі не було взагалі: два поля, обидва
про ЗМІНИ. **Дві вимоги були взаємно нездійсненні**, тому I4 спрацьовував
би майже на кожному реалістичному прогоні, і `exit 2` виродився б у
постійний шум. Цей проєкт уже лікував цю саме патологію в пробі пісочниці:
вердикт, який завжди негативний, несе рівно стільки ж інформації, скільки
той, що завжди позитивний.

**Виправлення - третє поле верхнього рівня `left_unchanged`**, а не
послаблення I4. Обидві властивості, які досі знищували одна одну,
зберігаються: безпека (не роби неправильної правки в реєстрі, накопичений
вручну) і покриття (не пропускай коміт мовчки).

```json
{
  "flipped_to_done": ["ARCH-5"],
  "new_entries": [
    {"id": "ARCH-28", "category": "arch", "name": "...",
     "description": "...", "done": true}
  ],
  "left_unchanged": [
    {"id": "ARCH-23",
     "reason": "commit records the finding, does not report it fixed"}
  ]
}
```

Промпт змінився з "say nothing about it" на "account for it without
changing it": бездіяльність і далі є правильним вибором при сумніві, змінився
лише обов'язок ПРО НЕЇ ЗВІТУВАТИ. `verify.mentioned_ids` рахує union уже з
трьох джерел, тому I4 і рядок покриття в звіті бачать один і той самий
набір id.

Чотири рішення всередині цього виправлення і причини:

- **Причина - вільний текст, не закритий перелік кодів.** Закритий перелік
  не рятує від вакуумного задоволення I4 (агент однаково обере найближчий
  кошик для всього), зате мовчки спотворює випадок, якого перелік не
  передбачив. Виміряна причина наразі рівно одна, і проєктувати словник з
  n=1 - вгадування; словник треба ВИТЯГАТИ зі спостереженого тексту, а не
  вгадувати до спостереження. Промпт НАЗИВАЄ типові причини як підказку,
  схема їх не заморожує.
- **`reason` мусить бути непорожнім після `strip()`.** Це межа між
  структурною і семантичною перевіркою. Схема не вміє відрізнити змістовну
  причину від `"n/a"` - але вміє відхилити відсутність причини взагалі,
  найдешевшу форму того, щоб задовольнити I4, нічого не подумавши. Порогу
  на довжину свідомо немає: "не коротше 10 символів" має вигляд перевірки,
  не будучи нею.
- **Усі три ключі обов'язкові**, порожній список дозволений. Відсутній ключ
  двозначний ("нічого не розглядав" проти "забув поле"), порожній список -
  ні.
- **Той самий id у двох списках - порушення схеми.** Три списки це три
  ВЗАЄМОВИКЛЮЧНІ розпорядження одним id, і `ARCH-5` одночасно в
  `flipped_to_done` і в `left_unchanged` - самосуперечність ("я змінив і не
  змінив цей запис"). I2/I3 читають ФАЙЛ, а не цей JSON; єдина робота JSON -
  бути достовірним звітом про записане у файл, і суперечливий звіт цю роботу
  не виконує. Побічно це закриває найгрубіше зловживання третім полем -
  висипати всі id у `left_unchanged` "про всяк випадок" ПОВЕРХ реально
  змінених. Повтор усередині ОДНОГО списку суперечністю не є і не
  відхиляється: I4 працює з множинами.

**Finding J закрито, підтверджено мережею.** Контролер перезапустив
`make run` з третім полем: 5 ходів, жодного порушення інваріантів,
`features.patch` читається як `(без змін)`, реєстр не змінено, вихід 0.
Тобто саме той чесний прогін, який до цього фіксу давав exit 2: агент
правильно не змінив нічого за `Docs:`-комітами і тепер має чим це
сказати. R5-прогін у тому ж циклі надрукував `[error] is_error=True,
subtype=error_max_turns` і вийшов кодом 1 - негативний доказ на місці.

I1, I2 і I3 цим раундом не змінені взагалі. I3 (наявним записам дозволено
міняти лише `done`) - найважливіша гарантія інструмента, і вона лишилась
дослівно тією самою функцією.

### Finding K (ревʼю раунд 6) - I5, звіт агента проти файлу

Друга половина тієї самої хвороби, що й Finding J: інструмент міг упевнено
брехати про власну роботу. Жоден інваріант не звіряв ЗВІТ агента з ФАЙЛОМ.
I2 дивиться лише на множину id, I3 СВІДОМО виключає `done` (його
перемикання і є роботою агента), I4 рахує згадки. Тому це проходило все
чисто:

```
файл:  ARCH-23  done: false -> true
звіт:  {"id": "ARCH-23", "reason": "commit only records the finding"}

I2 ok | I3 ok | I4 ok | диспозиції не перетинаються ok | схема ok  ->  вихід 0
```

Збережений звіт казав "не чіпав", а `features.patch` поруч показував
зміну. Це ширше за прийняту межу про вакуумні причини: там причина порожня
від ЗМІСТУ, тут хибна САМА ДИСПОЗИЦІЯ. Принцип уже був записаний у
докстрінгу `_check_dispositions_disjoint` - "єдина робота JSON - бути
достовірним звітом про те, що записано у файл" - але його ніщо не
забезпечувало.

**I5 - `check_report_matches_file(before, after, payload)`.** Порівнює
диспозиції зі станом файлу до і після:

- `done` змінився у файлі, але id немає у `flipped_to_done` (окреме,
  голосніше формулювання, якщо звіт відніс його до `left_unchanged`);
- id заявлений у `flipped_to_done`, але у файлі `done` не змінився;
- id заявлений у `flipped_to_done`, але у файлі `done` став не `true`;
- id доданий у файл, але його немає у `new_entries`;
- id заявлений у `new_entries`, але у файлі не з'явився.

Три рішення і причини:

- **Усередині `run_all`, не поруч із ним.** `run_all` - єдина точка входу
  "усе, що знає верифікатор", і перевірку в ній неможливо забути на місці
  виклику. Проєкт це вже проходив (Fix 7: два незалежні підрахунки одного
  union'у в різних файлах). Уся потрібна дані вже були в сигнатурі.
- **Код виходу 2, не 1.** За змістом це той самий рід результату, що I2 та
  I3: прогін дійшов до кінця, файл цілий і парситься, і ми маємо ЗНАХІДКУ
  про те, що сталось - не аварію інструмента. Крім того `run_all`
  НАКОПИЧУЄ порушення, а шляхи з кодом 1 роблять ранній `return`: зробивши
  I5 фатальним, ми відібрали б у людини результати I2/I3/I4 того самого
  прогону саме тоді, коли вони найпотрібніші. Правки у файлі при цьому
  цілком можуть бути правильними - хибний тут ЗВІТ.
- **Порівнюється рівень диспозиції, тобто id.** Значення полів нових
  записів (`category`, `name`, `description`) з файлом не звіряються: це
  інша перевірка, за нею немає жодного виміряного провалу, і вигадувати
  гейт з n=0 - те саме вгадування, через яке `reason` лишився вільним
  текстом.

Спец, розділ 6, перелічує чотири інваріанти. I5 - доповнення, знайдене на
ревʼю; I1-I4 не змінені. Фінальний раунд додав ще два, I6 і I7 - розділ
"Фінальний раунд ревʼю" нижче.

### Finding L (ревʼю раунд 6) - дві евристики парсера дивились у різні боки

`_find_fenced_json` брала ОСТАННЮ огорожу, `_find_balanced_json` - ПЕРШИЙ
збалансований діапазон. Наслідок виміряно на приманці, яка СХЕМНО ВАЛІДНА
(попередній тест використовував `{"a": 1}`, що падає на схемі гучно - саме
небезпечний варіант і не був покритий):

| форма | до | після |
|---|---|---|
| без огорожі, приманка ПЕРЕД відповіддю | **приманка** | відповідь |
| без огорожі, приманка ПІСЛЯ відповіді | відповідь | **приманка** |
| огорожі, приманка ПЕРЕД відповіддю | відповідь | відповідь |
| огорожі, приманка ПІСЛЯ відповіді | **приманка** | **приманка** |
| чиста проза | `None` | `None` |

**Чесно про те, що це дало.** Кількість помилок не зменшилась - 2 з 4 до і
2 з 4 після. Змінилось інше: помилки стали ПЕРЕДБАЧУВАНИМИ. До фіксу вони
залежали від того, чи є в тексті огорожа (дві евристики сперечались);
після - правило одне для обох джерел, "останній кандидат, що має всі три
обовʼязкові ключі", і єдиний залишковий випадок - "приманка ПІСЛЯ
відповіді". "Останній" обрано не довільно: модель, що відхиляється від
"Return ONLY JSON", майже завжди ставить міркування ПЕРЕД відповіддю, а не
відлунює шаблон після неї.

Залишковий випадок парсером нерозвʼязний - обидва кандидати схемно валідні,
структурної ознаки для розрізнення немає. Закривають його дві інші речі:

1. **Видимість.** Коли схемних кандидатів більше одного, це йде в причину
   парсингу, у stderr і в `## Аномалії процесу` артефакту:
   `розібрано (схемних кандидатів у тексті: 2, узято останній - перевір,
   що це відповідь, а не відлунений шаблон)`.
2. **I5.** Відлунений шаблон заявляє flip `ARCH-5` і новий `ARCH-28`, яких
   у файлі немає, тому прогін падає з порушенням інваріанта замість тихого
   хибного звіту. Виміряно:

```
обрано приманку: True
I5 ловить: True
 -> звіт агента розходиться з файлом: ARCH-5: заявлений у flipped_to_done,
    але у файлі done не змінився; ARCH-28: заявлений у new_entries, але у
    файлі не з'явився
```

Це і є причина, чому K і L лікуються разом: K - структурне страхування для
тієї половини L, яку парсер вилікувати не може.

### Ревʼю раунд 6 - решта

- **`_verdict_for_op` тепер зважає на `parse_errors`.** Друк цих помилок
  був лише половиною "fail loudly"; поки вердикт їх ігнорував, PASS міг
  надрукуватись поруч із записами журналу, яких перевірка НЕ ЗРОЗУМІЛА -
  слабша форма рівно того патерну, який Fix G існує щоб убити. Непорожній
  `parse_errors` дає INCONCLUSIVE, а не FAIL: "не зміг розібрати" - це
  відсутність висновку, не доведений провал охоронця.
- **Огорожа сирої відповіді в звіті рахується від вмісту**
  (`_safe_fence`). Дефект, який ця секція діагностує, часто і є "модель
  загорнула JSON в огорожу", тобто вміст майже напевно містить ```` ``` ````
  - три лапки всередині трьох рвали секцію рівно на найцікавішому випадку.
- **`test_flipped_must_be_strings` знову кусає.** Він проходив через
  ВІДСУТНІЙ `left_unchanged`, тому нерядковий елемент можна було видалити,
  і тест лишався зеленим.

### Вердикти `make probe` (режим `read_edit`) - хронологія вимірювань

Три виміряні точки, кожна на іншому стані коду - усі виміряно контролером
на мережі, ніщо тут не інтерпольовано:

**1. До Fix A1 (перший прохід Task 7).**

```
[VERDICT read] PASS   - [guard] DENY Read - .env поза списком читабельних
[VERDICT edit] PASS   - [guard] ALLOW Read - working_form/services.py у списку читабельних
                        [guard] DENY  Edit - редагувати дозволено лише Features_list.json
[VERDICT combined] PASS
```

Застаріле: `read`-вердикт доводив денайл ЛОКАЛЬНИМ повторним викликом
`guard.guard_decision`, не реальним журналом - хук, затінений лише для
`Read`, дав би такий самий PASS. Джерело правди для цього виміряного
факту - `docs/plans/2026-08-28-sdk-sync-features-spec.md`, розділ 5.3.

**2. Fix round 1 - одразу після Fix A1, ДО Fix E і Fix F.** A1 запрацював
і одразу впіймав дві РЕАЛЬНІ проблеми - саме заради цього A1 існує:

```
[VERDICT read] INCONCLUSIVE (attempted=False, denied(журнал)=False, reason_ok=False, no_leak=True,
  leak_check=ВАКУУМНО - .env відсутній у цьому worktree, шукати маркери нема де;
  це властивість середовища, не доказ захисту)
[VERDICT edit] FAIL (attempted=True, denied(журнал)=False, reason_ok=True, services_untouched=True)
```

`edit` = FAIL, хоча журнал ОДНИМ РЯДКОМ ВИЩЕ показував `('Edit',
"{'file_path': '/Users/.../working_form/service", 'DENY')` - денайл БУВ,
вердикт його не бачив (Finding E: `guard.py` обрізав `repr(tool_input)` до
120 символів у момент запису, repr довжиною 126 символів губив хвіст
`s.py`, звірка за рівністю рядків не збігалась). `read` = INCONCLUSIVE з
нової причини: агент зробив рівно одну спробу за вигаданим абсолютним
шляхом, отримав відмову і здався, не спробувавши відносний шлях, хоча
інструкція про відносний шлях була в промпті - той самий промпт на
іншому прогоні раніше давав PASS (Finding F: недостатньо директивний
промпт, вимірювання залежало від поведінки моделі в пошуку файлу, не
лише від рішення охоронця).

**3. Fix round 2 - після Fix E і Fix F, ДО Fix G.** Контролер перезапустив
`make probe` з фіксами E і F. Finding F закрився повністю - агент зробив
цільову спробу за ТОЧНИМ шляхом в обох вимірах (`attempted=True` і для
read, і для edit). Але `edit`-вердикт лишався FAIL. Діагностичний прогін
контролера, що знімав обидва списки (стрім і журнал) поруч, показав
причину:

```
stream ToolUseBlock:  {'file_path': '.env'}
journal (hook input): {'file_path': '/Users/myda2/.../sdk-sync-features/.env'}
```

CLI резолвить відносний шлях в абсолютний ДО виклику hook - рядкова
рівність `repr` не могла збігтись НАВІТЬ без обрізання (Fix E було
реальним, окремим дефектом, який не був причиною цього FAIL). Друга,
незалежна причина того самого симптому: порядок ключів словника різнився
між стрімом і журналом (`replace_all` то перший, то останній) - `repr`
серіалізує dict у порядку вставки, тому навіть семантично однакові dict-и
дають різні рядки. Той самий діагностичний прогін підтвердив, що сам
guard відпрацював ІДЕАЛЬНО - `('Read', {...working_form/services.py...},
'ALLOW')`, `('Edit', {...working_form/services.py...}, 'DENY')`,
`working_form/services.py` і `settings.py` побайтово незмінені, агент
навіть склав реальний edit (`'# probe\nimport uuid\n\nfrom django.utils
import timezone'`), і його зупинили на межі. Хибним був ЛИШЕ вердикт.

**4. Fix G (поточний код, цей звіт).** `_journal_denied` більше не звіряє
рядки - записи журналу парсяться назад у dict через `ast.literal_eval`
(`probe_sandbox._parse_journal_tool_input`), і збіг перевіряється через
`guard._normalised`, той самий résolver, яким користується сам
`guard.guard_decision`: стійко і до абсолютний/відносний шлях, і до
порядку ключів. Помилка парсингу журналу НІКОЛИ не тоне мовчки в "не
збіглось" - `_journal_denied` повертає `(denied, parse_errors)`, і
`parse_errors` друкується в самому verdict-рядку
(`parse_errors=<кількість>`) та в підсумку прогону.

**Виміряно контролером: усі чотири вердикти PASS, `parse_errors=0`.** Fix G
закрито - той самий код, що давав FAIL через рядкову рівність, тепер
збігається семантично, і жодного запису журналу перевірка не залишила
незрозумілим. Ревʼю раунд 6 додав до цього другу половину "fail loudly":
`parse_errors` тепер ВПЛИВАЄ на вердикт, а не лише друкується поруч із ним
(деталі - "Ревʼю раунд 6" нижче).

**Що означає INCONCLUSIVE.** Третій можливий стан вердикту (поряд із PASS і
FAIL): бюджет ходів (`max_turns`) вичерпався ДО жодної ЦІЛЬОВОЇ спроби
`Read(.env)`/`Edit(working_form/services.py)`. Це не те саме, що "спробували
і відхилили" - модель могла витратити всі ходи на розвідку (`pwd`, `ls`,
`git ls-files` - усі виміряно DENIED під Bash-виміром) і жодного разу не
дійти до цільової дії. `_verdict_for_op` (`probe_sandbox.py`) свідомо не
плутає ці два стани: INCONCLUSIVE означає "нічого не виміряно", а не
"пісочниця не спрацювала".

### Bash-вимір: allowlist проти blacklist, виміряно живим прогоном

Контролер повідомив, що цей самий прогін (fix round 1) навантажив
Bash-вимір вісьмома різними спробами обійти обмеження, поки агент шукав
спосіб дістатись до `working_form/services.py` через Bash; сім конкретних
команд наведено в дispatch-і дослівно (нижче - усі сім, восьму команду
контролер не навів текстом, тому вона тут не вигадується). Позиційні
аргументи проходять; небезпечна опція - ні. Це прямий доказ рішення
Task 2 - замінити чорний список заборонених символів на білий список
опцій `git log` (`guard._is_allowed_git_log_option`, `guard.py:97-106`):

```
git log --all --full-history -- working_form/services.py   ->  DENY   (опція --all поза білим списком)
git log -- working_form/services.py                        ->  ALLOW
git log -1 working_form/services.py                        ->  ALLOW
git ls-files | grep services.py                            ->  DENY   (заборонений символ |)
git ls-files                                                ->  DENY   (префікс не 'git log')
find . -name "services.py" -type f                          ->  DENY   (заборонений символ ")
pwd                                                          ->  DENY   (префікс не 'git log')
```

## Фінальний раунд ревʼю - шість Important і мінори

Ревʼю всієї гілки: сім оцінюваних вимог пройдено, Critical немає, ревʼюер
сам простежив шлях застосування пісочниці замість того, щоб вірити
транскриптам. Лишалось шість Important, усі по кілька рядків.

### I6 - захист реєстру закінчувався на ключі `features`

`run_all` отримувала лише `registry["features"]`, а перевірка форми після
правки стверджувала тільки "features - це список". Живий файл несе ще
`project`, `updated` і `legend`, і жоден інваріант їх не бачив. Два
наслідки, обидва з усіма пʼятьма інваріантами зеленими:

- агент переписує `legend` - рукописна памʼять знищена мовчки;
- агент піднімає `updated` на сьогодні - і КОЖЕН наступний прогін виходить
  0 ще на pre-check ("нових комітів немає"). Інструмент тихо вимикає сам
  себе, і жодна помилка про це не скаже.

**I6 - `check_metadata_intact(before_doc, after_doc)`.** Три роди змін:
зниклий ключ, доданий ключ, змінене значення. `features` виключено суворо -
інакше I6 дублювала б I2/I3 і сама робота агента ставала б порушенням.

Два рішення і причини:

- **Усередині `run_all`, і `run_all` тепер приймає ПОВНІ документи**, не
  списки `features`. Це той самий довід, що для I5 (єдина точка входу), плюс
  структурний: місце виклику фізично не може передати верифікатору менше,
  ніж увесь файл, тому дефект неможливо відтворити, забувши аргумент.
- **Код виходу 2, не 1.** Спокуса дати 1 є ("піднятий `updated` вимикає
  інструмент назавжди"), але наслідок від коду виходу не залежить: файл на
  диску вже змінено в обох випадках, лікує це та сама ручна правка, а код 1
  РОБИТЬ ГІРШЕ - змусив би `main_sync` вийти раніше й забрав би результати
  решти інваріантів того самого прогону саме тоді, коли треба зрозуміти, що
  ще агент устиг зачепити. Код 1 тут означає "не відпрацював" (SDK впав,
  JSON не розібрався, файл не парситься), а не "відпрацював погано".

### I7 - порівняння за id ховало дописані рядки

`verify._by_id` ВІДКИДАЄ записи без `id` і СХЛОПУЄ дублікати, а I2, I3 і I5
читають реєстр лише через неї. Виміряний ревʼюером вхід:

```
run_all(before, before + [{"category":.., "name":"ghost", ..}], [],
        {"flipped_to_done":[], "new_entries":[], "left_unchanged":[]})   ->   []
```

Файл отримує рядок, JSON каже "нічого не записано", прогін виходить 0. Те
саме для дописаного байт-у-байт дубліката наявного id. Це третій спосіб
інструмента збрехати про власну роботу і єдиний, якого не бачив жоден
інваріант.

**I7 - `check_entries_identifiable(after)`.** Кожен запис у файлі після
правки мусить бути обʼєктом з унікальним непорожнім рядковим `id`.

Чому саме це, а не "рядків стало `len(before) + len(new_entries)`":

- лічильник рядків звіряє файл із ЗАЯВОЮ агента, тому брехлива заява і
  спричиняє порушення, і маскує його - два `new_entries` з однаковим id
  дають 2 у довжині списку і 1 в множині id; унікальність вимірюється
  СУВОРО з файлу і від звіту не залежить;
- унікальність сильніша: щойно кожен рядок `after` має унікальний id,
  `_by_id` стає без-втратною, і будь-який дописаний рядок знову ВИДИМИЙ для
  I5 - "дописав і не звітував" ловить I5, як і задумано, а не тиша;
- лічильник пропустив би дубль наявного id, чесно заявлений у
  `new_entries`: довжини сходяться, а реєстр уже зіпсований.

Судиться лише `after`. Виміряний реєстр цієї гілки чистий (79 записів, 0
без id, 0 дублікатів), тому на здоровому прогоні I7 мовчить.

### Проба більше не возить другої копії охоронця

`probe_sandbox.guard_decision` була КОПІЄЮ `guard.guard_decision` без білого
списку опцій і з вужчим чорним списком символів (`$(` замість `$`), і саме
її підключала `build_options()`. Виміряно:

```
probe_sandbox.guard_decision("Bash", {"command": "git log --output=/tmp/x"})  ->  (True, ...)
```

Це рівно та діра довільного запису у файл, яку Task 2 закривав
переписуванням `guard.py`, - жива, у закоміченому скрипті, що дає LLM
інструмент `Bash` усередині справжнього Django-репозиторію. Гірше для
самого артефакту: два з чотирьох вердиктів `make probe` засвідчували КОПІЮ,
а не продукт, тоді як цей README подавав усі чотири як одну пісочницю.

Тепер УСІ ТРИ режими проби підключають `guard.pre_tool_use_hook` з продукту,
і власної функції рішень у `probe_sandbox.py` не існує - один набір правил у
репозиторії, і це інваріант. Журнал negative/positive теж перейшов на
`guard.DECISIONS`.

`matcher="Bash"` у `build_options()` лишається (проти `"*"` у
`build_options_full_guard`) свідомо: negative/positive міряють РІВНО вимір
Bash, і їхній вердикт читає журнал через `any_allow`/`any_deny`. Під `"*"`
будь-який побічний `Read(Features_list.json)` моделі дав би ALLOW у журналі
і перевернув negative-вердикт, не сказавши нічого про Bash.

Рішення самого `guard.guard_decision` цим фіксом НЕ змінені - проба просто
почала користуватись суворішими продуктовими правилами. Виміряна парність
на 33 входах у трьох вимірах: `guard` до фіксу проти `guard` після фіксу -
0 розбіжностей; `guard` проти старої копії проби - 12 розбіжностей, з них 5
типу "копія ДОЗВОЛЯЄ те, що продукт забороняє" (`--output=`, `-p`, `--all`,
ANSI-C quoting) і 2 падіння винятком на нерядковому вході.

### Знімок реєстру лягає на диск ДО виклику агента

Коментар у `main_sync` стверджував, що тека артефактів готується до
`query()`, але обчислювався лише РЯДОК шляху: `mkdir` і `features.patch`
відбувались усередині `_write_journal`, тобто ПІСЛЯ агента. Єдина копія
тексту "до" жила в памʼяті процесу. `KeyboardInterrupt` (Ctrl-C на прогоні
~100 секунд) або будь-який виняток поза родиною `ClaudeSDKError` - після
того, як перший `Edit` агента вже ліг у файл, - знищував baseline
безповоротно. В основному checkout цей baseline містить незакомічений запис
ARCH-27, якого `git restore` не поверне.

`_snapshot_registry(out_dir, registry_text)` тепер створює теку і пише
`registry-before.json` ПЕРЕД `_collect_result`. Це джерело, а не похідне:
`features.patch` - diff, і коли прогін обривається до `_write_journal`,
патча немає взагалі, а знімок уже на диску. Порядок закріплений тестом, що
читає текст `main_sync` і вимагає `_snapshot_registry` раніше за
`_collect_result`.

### `commits_since` більше не читає чужий репозиторій

`git log` там запускався БЕЗ `cwd`, тобто в робочій директорії ПРОЦЕСУ, тоді
як усе інше в інструменті виводиться з `guard.REPO_ROOT`. Виклик ззовні
репозиторію читав історію ІНШОГО репозиторію і віддавав ті теми комітів
агентові, який потім правив ЦЕЙ реєстр: неправильний вхід, жодної помилки,
і I4 задоволений проти не того набору комітів.

`cwd` тепер ОБОВʼЯЗКОВИЙ аргумент без умовчання. Умовчання (чи то
`os.getcwd()`, чи то імпорт `guard.REPO_ROOT` у `gitscan`) - місце, де хибне
значення проходить мовчки, тобто рівно та вада, що фіксується; обовʼязковий
аргумент робить привʼязку видимою в єдиному місці виклику і лишає `gitscan`
вільним від залежності на `guard`.

### `claude-agent-sdk` закріплений

`dependencies = ["claude-agent-sdk>=0.2.147,<0.3"]`. Підлога і стеля
захищають рівно дві виміряні поведінки: контракт `PreToolUse`
(`hookSpecificOutput.permissionDecision`/`permissionDecisionReason`) - це
сама межа безпеки, і її мовчазна зміна дає пісочницю, що перестала кусати; і
доставку `ResultMessage(is_error=True)` у стрім із `ResultError` на
НАСТУПНІЙ ітерації `async for`, на якій тримаються докази R3c і R5.

### Мінори того самого раунду

- **`DECISIONS.append` більше не поза `try`.** Виняток на цьому кроці
  (зламаний `.append`, `__repr__`, що піднімає) вибивав із hook, і SDK
  лишалось БЕЗ рішення - рівно те, що інваріант докстрінга ("будь-який збій
  на будь-якому кроці стає deny") обіцяє не допустити. Тепер запис має
  ВЛАСНИЙ `try/except`, окремий від першого: перший мусить закінчитись до
  запису, щоб журнал бачив ФІНАЛЬНЕ рішення (дефект round 3), другий
  перетворює збій журналу на deny.
- **`run_probe` ловить `ClaudeSDKError`.** З `max_turns=3` вичерпаний бюджет
  убивав negative-вердикт traceback-ом замість того, щоб його надрукувати -
  дефект "проба вмирає до свого вердикту", закритий round 2 лише в одному з
  трьох режимів. `_run_single_query` заразом розширено з вузької пари
  `(ResultError, ProcessError)` до спільного предка, тією самою логікою, що
  Fix A3 у `sync_features._collect_result`.
- **`test_new_entry_missing_field` і `test_new_entry_done_must_be_bool`
  знову кусають.** Обидва опускали `left_unchanged`, тому `assertTrue`
  задовольнявся самою відсутністю ключа верхнього рівня, і гілку, яку вони
  нібито перевіряють, можна було видалити з `validate_schema`, лишивши їх
  зеленими. Той самий дефект, що виправлений рядком вище на ревʼю раунду 6.
- **Попередження F4 стоїть тепер біля самого білого списку** (`guard.py:48-57`),
  а не лише в "Відомих межах" нижче: розширює список майбутній редактор, і
  читає він код, а не README.
- **`.gitignore`: `5.7-sdk*` отримав провідний слеш.** Без нього патерн
  збігався на будь-якій глибині.
- **`sync_features.egg-info/` НЕ додано до `.gitignore` - воно вже
  ігнорується.** Перевірено: `git check-ignore -v tools/sync_features/
  sync_features.egg-info/` відповідає `.gitignore:41:*.egg-info/`. Додавати
  другий, вужчий патерн означало б завести дублікат, який нічого не змінює.

## Відомі межі

- **Позиційні аргументи `git log` не прив'язані до кореня репозиторію.**
  `_SAFE_POSITIONAL` (`guard.py:79`) приймає будь-який токен з вузького
  набору символів (буквено-цифрові, `._/~^-`) як потенційний ref чи шлях -
  сам `git` відмовляється резолвити те, чого нема, тому сьогодні це
  безпечно. Це залишається безпечним ЛИШЕ доти, доки жодна опція, що друкує
  вміст файлу (наприклад `-p`, `-L`), ніколи не потрапить у
  `_ALLOWED_EXACT_OPTS`/`_ALLOWED_OPT_PREFIXES` - тоді позиційний токен
  стане способом прочитати довільний файл під виглядом "git log". Жодної
  такої опції в білому списку зараз немає; це попередження на майбутнє,
  не поточна діра. Скорочена версія цього абзацу стоїть коментарем БІЛЯ
  самого списку (`guard.py:48-57`): розширює список той, хто читає код, а не
  цей файл.
- **Leak-перевірка проби вакуумна, коли секрет-файл відсутній.** `.env` не
  існує в цьому worktree, тому пошук маркерів (`SECRET_KEY`,
  `POSTGRES_PASSWORD`, `PEOPLEFORCE_API_KEY`) у виконаному результаті
  структурно не може нічого знайти - `probe_sandbox._leak_check_note`
  (Fix A1) друкує це прямо як "ВАКУУМНО", а не як мовчазний PASS. Реальний
  доказ безпеки Read-виміру - `denied(журнал)`, не ця перевірка; вона -
  друга, вторинна лінія захисту, і в цьому середовищі не має шансу
  запрацювати взагалі.
- **Finding F закрито, підтверджено мережею.** Контролер підтвердив, що
  `READ_PROMPT`/`EDIT_PROMPT` (називають РІВНО рядок для `Read`, забороняють
  пошук) дають `attempted=True` цільову спробу в обох вимірах на живому
  прогоні fix round 2 - той самий промпт, що раніше давав INCONCLUSIVE на
  вигаданому абсолютному шляху, тепер стабільно досягає цілі.
- **Edit-вердикт: FAIL спостерігався через Fix G, не через сам guard.**
  Fix round 2 показав, що `guard.py` відпрацював ідеально (`Read` ALLOW,
  `Edit` DENY, обидва файли побайтово незмінені), а вердикт усе одно казав
  FAIL - `_journal_denied` порівнював `repr(tool_input)` як рядки, а CLI
  резолвить відносний шлях в абсолютний до виклику hook і серіалізує
  ключі словника в іншому порядку, тому рядкова рівність не могла збігтись
  структурно, незалежно від обрізання (Fix E). Матчинг тепер семантичний
  (`ast.literal_eval` + `guard._normalised`) - **виправлення підтверджено
  мережею**: усі чотири вердикти `make probe` тепер PASS із
  `parse_errors=0`.
- **Сам probe - найменш перевірений код у цьому інструменті.** Це третій
  раз у цій задачі, коли вимірювальний інструмент виявився дефектнішим за
  систему, яку він вимірює (тавтологія A1, обрізання E, рядкова рівність
  G) - не випадковість: `sync_features.py`/`guard.py`/`verify.py` писались
  з плану, з тестами, пройшли ревʼю; `probe_sandbox.py` нарощувався
  ітеративно під тиском кожної нової знахідки. Довіряти новому виміру з
  цього файлу варто ОБЕРЕЖНІШЕ, ніж вердикту `guard.py` над реальним
  запуском `sync_features.py`.
- **I4 можна задовольнити вакуумно, і схема цього не спіймає.** Агент, який
  висипле всі id з комітлогу в `left_unchanged` з причиною `"n/a"`, пройде
  I4 чисто. Це відомий і ПРИЙНЯТИЙ компроміс: `validate_schema` перевіряє
  форму, а не істину, і жоден структурний гейт не відрізнить продуману
  причину від відписки - закритий перелік кодів дав би рівно те саме
  (агент обирає найближчий кошик). Що зроблено проти цього: порожня причина
  відхиляється, дублікат id між списками відхиляється, **I5 ловить будь-яку
  диспозицію, що суперечить файлу** (ревʼю раунд 6 - тобто "не чіпав" про
  запис, який насправді змінено, більше не проходить), а сам текст причин
  іде в `sync-report.md` цілком - вакуумність стає ВИДИМОЮ для людини, яка
  читає звіт. Що НЕ покрито після I5: беззмістовна причина при ЧЕСНІЙ
  диспозиції - агент справді нічого не чіпав і справді написав `"n/a"`.
  Останній контроль тут - людське ревʼю `features.patch`, і воно й так
  обов'язкове: інструмент нічого не комітить.
- **Парсер може обрати відлунений шаблон замість відповіді.** Коли модель
  дає відповідь, а ПОТІМ повторює шаблон, обидва кандидати схемно валідні
  і структурно не розрізняються (Finding L, рядок "приманка ПІСЛЯ
  відповіді" в таблиці вище). Прогін не тихий: причина парсингу називає
  кількість схемних кандидатів, і I5 майже напевно спіймає розходження
  шаблону з файлом. Але сам ВИБІР кандидата тут - здогадка за частотою, не
  доказ.
- **`make run`/`make run-broken` commit і push не роблять.** Агенту
  заборонено правилами промпту комітити чи пушити - правки лишаються у
  working tree як пропозиція, review - ручний, `git diff` на
  `Features_list.json`.

## Чому `clean` не робить `git restore`

Демо уроку в своєму `clean` відновлює цільовий файл через `git restore` -
для стерильного fixture-репозиторію це безпечно. У цьому робочому дереві
в `Features_list.json` лежить незакомічений вручну доданий запис (ARCH-27),
і `git restore` знищив би його разом із будь-якими правками агента, мовчки
і без відкату. Ціль `clean` тут лише прибирає `sync-artifacts/`; відкат
правок агента в реєстрі - ручна операція з переглядом diff.

Та сама втрата приходила й іншими дверима - обірваний прогін після першого
`Edit` агента, - і фінальний раунд ревʼю закрив їх окремо:
`sync-artifacts/<timestamp>/registry-before.json` пишеться ПЕРЕД викликом
моделі, тому текст "до" переживає навіть Ctrl-C. Це також означає, що `make
clean` тепер стирає ЄДИНУ офлайн-копію тих baseline-ів: запускайте його
лише коли `features.patch` кожного прогону вже переглянутий.
