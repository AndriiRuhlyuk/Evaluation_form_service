# 0001 — Виконувати AI-оцінювання у фоновому воркері як окремій поверхні

- **Status:** Accepted
- **Date:** 2026-09-09
- **Deciders:** Andrii Rykhliuk (власник фічі), Architect

## Context

PRD §7 задає дві вимоги, які разом не лишають місця для синхронного виклику. Перша: машинні бали
мають з'явитись протягом години після прикріплення тексту — тобто хвилини затримки прийнятні, і
чекати на них у HTTP-запиті немає причин. Друга, жорсткіша: доступність машинного оцінювання (99.0%
на місяць) рахується **окремо** від конвеєра, а 100% сценаріїв найму мають проходити без тексту
інтерв'ю взагалі. Окремий показник доступності має сенс лише для окремого процесу з власним життєвим
циклом. У репозиторії такий процес уже запущений — сервіси `celery` і `celery-beat` у
`docker-compose.yaml` — але зараз він несе одну дрібну періодичну задачу `update_evaluation_statuses`,
без політики повторів і без захисту від подвійного виконання.

## Decision drivers

- QG-1 «Ізольованість конвеєра від збою машинного оцінювання» (§1) — жоден сценарій найму не залежить
  від того, чи працює AI evaluator.
- PRD §7: доступність машинного оцінювання 99.0% на місяць, рахується окремо від конвеєра.
- PRD §7: 100% сценаріїв найму проходять без тексту інтерв'ю (перевіряється прогоном із вимкненою
  залежністю).
- PRD §7: готовність машинних балів ≤ 60 хв після прикріплення — вікно фонової задачі, не запиту.
- §2 Constraints: Celery 5.5.3 + django-celery-beat уже в стеку; нової інфраструктури не потрібно.

## Considered options

1. **`[backend-service, worker]`** — фіча оголошує дві поверхні: HTTP-сервіс із новими ендпоінтами і
   фоновий виконавець, який робить саме оцінювання.
2. **`[backend-service]` без окремої поверхні воркера** — задача виконується в тому самому Celery, але
   не визнається окремою поверхнею; контракт черги ніде не описується, окремого SLO немає.
3. **`[backend-service, worker, web-frontend]`** — додатково будуємо браузерний UI для екранів
   порівняння, картки й розбору.
4. **Синхронний виклик evaluator прямо в обробнику запиту** на прикріплення тексту.

## Decision outcome

**Chosen: варіант 1 — `[backend-service, worker]`.** Варіант 4 відпадає одразу: він ставить зовнішню
модель у синхронний шлях користувача і робить недосяжною вимогу «100% сценаріїв найму проходять без
тексту». Варіант 2 виконав би ту саму роботу кодом, але не дав би того, заради чого поверхня
оголошується: без неї наступні етапи не згенерують контракт черги (`contracts/events.md`), §5 не
намалює воркер окремим контейнером, а тести не дістануть рівня «задача виконалась повторно і не
продублювала бал». Варіант 3 був **реальним вибором, а не формальністю**: він стояв у переліку поверхонь і його зважували.
Відхилено за вартістю — у репозиторії немає ні фронтенду, ні дизайн-системи, ні компонентної бібліотеки,
тож UI будувався б з нуля, і сама ця робота більша за все AI-наповнення разом. Рядок `CLAUDE.md`
«No frontend here» описує **стан** репозиторію, а не забороняє фронтенд: за іншого бюджету варіант 3 був
би припустимим, і саме тому він лишається в переліку розглянутих, а не в межах обсягу.

## Consequences

**Positive**
- Вимкнення AI evaluator не ламає жодного сценарію найму: задача не ставиться або падає, форма живе далі.
- Доступність машинного оцінювання вимірюється окремо, як вимагає PRD §7, бо це окремий процес.
- Наступні етапи автоматично дістають потрібні артефакти: контракт черги, окремий контейнер у §5,
  рівень тестів на повторне виконання.

**Negative**
- Целері-воркер ділить Redis із channel layer WebSocket-каналів working form: довга черга LLM-задач
  може конкурувати з повідомленнями реального часу. Рядок ризику в §11.
- Наявна задача `update_evaluation_statuses` не має ні політики повторів, ні захисту від подвійного
  виконання — тобто в репо немає прецеденту, з якого можна списати форму надійної задачі.
- Стан «бали ще рахуються» стає видимим користувачу і потребує власного представлення в API.

**Neutral**
- Перехід на синхронний виклик пізніше технічно можливий, але означав би відмову від окремого SLO —
  тобто зміну вимоги PRD, а не лише коду.
