## 1. Брейншторм вдосконалень

### 1.1 Продуктова частина

- **Від "форм" до "платформи найму"**: зараз сервіс закриває один етап — технічне інтерв'ю. Продуктовий вектор: повний цикл *підготовка → інтерв'ю → рішення → аналітика → розвиток найнятого співробітника (L&D)*.
- **AI як диференціатор**: автопідбір питань під вакансію, підказки оцінок, авто-саммері та "пам'ять" про кандидата — це те, чого немає в PeopleForce/ATS, і що робить продукт цінним саме для технічних команд.
- **Калібрування складності питань за даними**: реальна складність питання ≠ заявлена (Easy/Medium/Hard). Статистика відповідей дозволяє автоматично рекалібрувати difficulty і робити чесніші скоринги.
- **Бенчмаркінг кандидатів**: порівняння кандидата з попередніми кандидатами на цю ж вакансію/рівень ("кращий за 78% Middle Python за останній рік").
- **Мультитенантність** (довгостроково): продукт можна продавати іншим компаніям — потрібна ізоляція даних по організаціях.

### 1.2 Користувацька частина (UX)

- **Інтерв'юер**: "кокпіт інтерв'ю" — питання + таймер + швидкі оцінки 0–3 одним кліком + нотатки; офлайн-стійкість (autosave, optimistic UI); мобільна версія для оцінювання на льоту.
- **Рекрутер**: канбан кандидатів по вакансії; статуси фідбеків інтерв'юерів (хто ще не здав); нагадування в один клік; шаблони листів кандидату.
- **Hiring Manager**: зведена сторінка рішення — всі оцінки, розбіжності між інтерв'юерами (виділяти питання, де оцінки розійшлися ≥2 бали), AI-саммері, історія попередніх інтерв'ю кандидата.
- **Онбординг**: демо-дані та майстер створення першого шаблону; підказки в порожніх станах.
- **Сповіщення**: email + in-app (WebSocket вже є) про призначення на інтерв'ю, дедлайни фідбеку, запити на approve. У `tasks.py` вже є TODO під це.

### 1.3 Функціональна частина

- **Тести** — критичний борг: сервісний шар (clone_*, toggle_*_vote, publish), permissions, consumers. Без цього будь-який рефакторинг ризикований.
- **Нотифікації**: Celery-таски на email (нагадування за 24г/1г, "усі фідбеки зібрано").
- **Календар**: iCal/Google Calendar інвайти при створенні EvaluationForm, перевірка конфліктів інтерв'юерів.
- **Звіти**: PDF-експорт (WeasyPrint), захищені signed URLs замість публічних media-посилань, брендування звіту.
- **Аудит-лог**: хто/коли змінив питання, проголосував, змінив оцінку (django-simple-history або власна модель подій).
- **Пошук**: повнотекстовий пошук по банку питань (PostgreSQL FTS), фільтри по difficulty/topic/usage.
- **Імпорт/експорт** банку питань (CSV/JSON) для міграції з таблиць.

### 1.4 Архітектурна частина — Backend

- **Налаштування**: розділити `settings/base.py|dev.py|prod.py`; `ALLOWED_HOSTS`, CORS з env; секрети поза .env у проді (vault/secrets manager).
- **Медіа**: S3-сумісне сховище (django-storages) — зараз звіти в локальному media, що не масштабується і не безпечно.
- **Спостережуваність**: Sentry, структуровані логи (structlog), healthcheck-ендпоінти, Prometheus-метрики (client вже в requirements).
- **API**: версіонування `/api/v1/`; кешування довідників (Redis); пагінацію PAGE_SIZE=5 підняти/зробити настроюваною.
- **БД**: індекси під аналітичні запити; `pgvector` розширення — фундамент під AI-пам'ять та семантичний пошук питань.
- **AI-шар**: окремий app `ai_assistant` з провайдер-абстракцією (Claude API як основний), усі виклики — через Celery (async), з rate limiting, кешуванням і логуванням промптів/відповідей.
- **Безпека**: скоротити ACCESS_TOKEN_LIFETIME (зараз 6 год), CSP-заголовки, залежності — Dependabot.

### 1.5 Архітектурна частина — Frontend

- **SPA на Next.js/React + TypeScript**: сервіс уже ASGI/WebSocket-ready, а фронтенду немає — це головний блокер продуктової цінності.
- **Стек**: TanStack Query (кеш API), Zustand/Redux для стану, WebSocket-клієнт для working form (реюз існуючого `ws/working_form/<id>/`), UI-кіт (shadcn/ui), i18n (uk/en).
- **Ключові екрани**: конструктор шаблонів (drag&drop топіків/питань) → кімната узгодження working form (live-голосування, який уже підтримує бекенд) → кокпіт оцінювання → дашборди аналітики.
- **Автогенерація типів** з OpenAPI-схеми (drf-spectacular → openapi-typescript) — контракт фронт/бек без ручної синхронізації.

## 2. План реалізації (фази)

### Фаза 0 — Фундамент якості (1–2 тижні)

- [ ] Тести: services (clone/vote/publish), permissions, ключові API-флоу, consumer (QA-1)
- [ ] CI: GitHub Actions — black/flake8, тести, перевірка міграцій (QA-2)
- [ ] Розділення settings на base/dev/prod, env-driven ALLOWED_HOSTS/CORS (ARCH-1)
- [ ] Sentry + структуроване логування + healthcheck (ARCH-1)

### Фаза 1 — Функціональні quick wins (2–3 тижні)

- [ ] Email-нотифікації через Celery: призначення, нагадування, дедлайни фідбеку (FN-1)
- [ ] PDF-звіт + signed URLs для звітів (FN-3)
- [ ] Повнотекстовий пошук та розширені фільтри по банку питань
- [ ] Аудит-лог змін форм/оцінок (FN-4)
- [ ] API v1 + кешування довідників (ARCH-2)

### Фаза 2 — AI-ядро (4–6 тижнів)
> Новий app `ai_assistant`: провайдер-абстракція над Claude API, виклики через Celery, логування промптів, feature-флаги per-функція.

- [ ] **AI-підбір питань (AI-1)**: генерація/рекомендація питань за tech stack + topic + рівнем вакансії; врахування usage_count і статистики відповідей; статус `Question.source=GENERATED` вже закладено в моделі — генеровані питання потрапляють у working form через існуючий approve-флоу (інтерв'юери голосують, отже AI-контент проходить людську перевірку).
- [ ] **AI-асист оцінювання (AI-2)**: за коментарем інтерв'юера до відповіді — пропозиція балу 0–3 з обґрунтуванням; інтерв'юер завжди підтверджує вручну (human-in-the-loop, оцінка ніколи не ставиться автоматично).
- [ ] **AI-саммері інтерв'ю (AI-3)**: після сабміту всіх фідбеків — авто-генерація резюме кандидата (сильні/слабкі сторони, узгодженість оцінок, рекомендація) → у HTML/PDF-звіт і в ноту PeopleForce (зараз summary формується вручну).
- [ ] **Інтеграція з ноут-тейкером (AI-7)**: транскрипт інтерв'ю через API (Recall.ai / Fireflies / tl;dv — webhook після мітингу), сегментація транскрипту та мапінг відповідей кандидата на питання форми.
- [ ] **Незалежне AI-оцінювання + divergence-звіт (AI-8)**: AI оцінює кожну відповідь з транскрипту за тією ж шкалою 0–3 і вагами питань, що й інтерв'юер; звіт розбіжностей (питання, де AI ≠ людина, з обґрунтуванням обох оцінок) — інструмент контролю якості інтерв'ю та калібрування інтерв'юерів; агрегати розбіжностей живлять HR-аналітику Фази 4.

### Фаза 3 — Пам'ять про кандидата (3–4 тижні)

- [ ] `pgvector` + модель `CandidateInterviewMemory`: embeddings усіх Q&A, фідбеків і саммері по кожному кандидату (AI-4)
- [ ] Кандидат уже є сутністю (`Candidate`, unique email) — зв'язати всі його EvaluationForm у таймлайн
- [ ] При створенні нової evaluation form: показ історії ("інтерв'ювався 8 міс. тому на Middle, слабкі місця — async, SQL"), виключення вже поставлених питань з AI-підбору
- [ ] Семантичний пошук по банку питань (побічний ефект того ж embedding-шару)

### Фаза 4 — Аналітика (3–4 тижні)

- [ ] **Recruitment-аналітика (AI-5)**: воронка по вакансії/проєкту, time-to-decision, pass rate по tech stack/рівнях, калібрування складності питань (питання, які "всі завалюють" або "всі проходять")
- [ ] **HR-аналітика (AI-6)**: навантаження інтерв'юерів, консистентність оцінок (хто систематично суворіший/м'якший), розбіжності панелей, якість найму (зв'язка з подальшим перформансом — точка інтеграції з PeopleForce)
- [ ] Матеріалізація метрик: щоденні Celery-агрегати в окремі analytics-таблиці; API дашбордів; AI-генеровані insights ("за 3 міс. pass rate по Senior Python впав на 20% — питання по X перекалібровані")

### Фаза 5 — Frontend SPA (паралельно з фазами 2–4)

- [ ] Next.js + TypeScript, типи з OpenAPI-схеми (FE-1)
- [ ] MVP: авторизація (JWT) → список форм → кокпіт оцінювання
- [ ] Live-кімната working form на існуючому WebSocket API
- [ ] Конструктор шаблонів, дашборди аналітики

### Фаза 6 — База для L&D (4–6 тижнів)
> Ключова ідея: рушій "форма → питання → оцінка → звіт" універсальний. Інтерв'ю кандидата і оцінка скілів співробітника — один механізм.

- [ ] Узагальнити суб'єкт оцінювання: `Candidate` → абстракція `Evaluee` (кандидат | співробітник), щоб EvaluationForm працювала для внутрішніх assessment'ів (LD-1)
- [ ] Тип форми: `hiring` | `skill_assessment` | `performance_review`
- [ ] Компетенційна матриця: Topic → Competency з очікуваними рівнями по грейдах (Junior..Head — грейди вже є в Employee)
- [ ] Цикли переоцінки: періодичні assessment'и через celery-beat, трекінг прогресу скілів у часі (реюз пам'яті з Фази 3 — тепер про співробітника)
- [ ] AI-план розвитку: за результатами assessment — рекомендовані теми/матеріали, gap-аналіз до наступного грейду
- [ ] Місток hiring → L&D: найнятий кандидат конвертується у співробітника разом зі своєю інтерв'ю-історією — перший skill assessment будується на слабких місцях з інтерв'ю

## 3. Технічні принципи для AI-функцій

1. **Human-in-the-loop завжди**: AI пропонує (питання, бал, саммері) — людина затверджує. Жодне рішення щодо кандидата не приймається автоматично.
2. **Провайдер-абстракція**: інтерфейс `AIProvider` (generate_questions, suggest_score, summarize, embed) — Claude API як основна реалізація, mock для тестів.
3. **Асинхронність**: усі AI-виклики через Celery; результат — через WebSocket/polling; таймаути і retry.
4. **Аудит**: логування prompt/response/model/latency/cost по кожному виклику (окрема модель `AIInvocation`).
5. **Приватність**: PII-мінімізація в промптах (кандидат — за ID, не за ПІБ, де можливо); retention-політика для embeddings.
6. **Вартість**: кешування embeddings, батчинг, дешевша модель (Haiku) для рутинних задач, потужніша — для саммері та аналітичних insights.

## 4. Метрики успіху

| Напрям | Метрика | Ціль |
|---|---|---|
| Якість | Покриття тестами сервісного шару | ≥80% |
| AI-підбір | Частка AI-питань, схвалених інтерв'юерами | ≥60% |
| AI-скоринг | Збіг запропонованого балу з фінальним | ≥75% |
| Саммері | Час рекрутера на оформлення результату | −50% |
| Аналітика | Time-to-decision по вакансії | −30% |
| L&D | Співробітники з актуальною компетенційною матрицею | 100% |
